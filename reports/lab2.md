# 实验二报告：地址空间（ch4）

## 我实现的功能

本次实现三件事：一是重写时间获取与追踪两个系统调用，用页表把用户指针翻译成内核可访问的物理地址（跨页也正确），读写前检查用户位与读写权限，不可见时返回 -1，并保留“查询系统调用次数”的请求；二是实现内存映射调用，校验对齐、属性位、区间冲突与页帧余量，把属性位逐位翻译成内核页权限并强制加用户位，再按页建立映射；三是实现解除映射调用，整段已映射才放行，之后逐页清页表项、归还物理页帧。

## 具体实现

### 整体分层

两条内存映射调用从系统调用入口一路向下，共经过四层，每层只干一件事：

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 系统调用 | `os/src/syscall/process.rs` | 检查参数的**格式**：对齐、属性位、溢出 |
| 进程管理 | `os/src/task/mod.rs` | 通过 `current_task` 找到**当前 Running 的进程** |
| 进程（TCB） | `os/src/task/task.rs` | 检查该进程的**地址空间是否冲突** |
| 地址空间 | `os/src/mm/memory_set.rs` | 真正增删 `MapArea`、改页表、分配/回收物理帧 |

`TaskManager` 这一层看起来只是转发，但它解决了一个实际问题：系统调用只知道“是某个进程在调我”，拿不到那个进程的可变引用；所以用 `exclusive_access()`（单核版的 `RefCell`）取得 `inner` 的可变借用，再用 `current_task` 下标定位。这样对外只需要不可变借用。

### 1. 时间获取

拿到时间本身不难，难的是**往哪里写**：时间结构体的指针是用户虚拟地址，内核页表里根本看不到它，直接解引用会写坏内核数据。

- 先用 `translated_byte_buffer` 把它按页翻译成若干段内核可访问的可变字节切片，**跨页时自然分成两段**；
- 再把内核栈上构造好的时间结构体按字节逐段拷进去。

这也顺手回答了题面的 HINT：结构体被两页劈开时不用特判，分片拷贝天然支持。

### 2. 追踪

追踪的读写语义是“**以用户身份**读写一个用户地址”，所以必须自己走页表，还要检查权限。写了一个小工具函数来完成翻译：

1. 用 `PageTable::from_token` 临时造一个“页表视图”（不持有帧，只借根页号，不会误释放别人的帧）；
2. 调用 `translate` 拿页表项，先看有效位（返回 `Some` 不代表有效），再看用户位——**内核自己的映射没有用户位，不能让用户借追踪调用绕过去**；
3. 写要求可写、读要求可读；
4. 都通过才返回物理地址。ch4 内核是恒等映射，物理地址可以直接当指针用。

于是各种情况自然就对了：

- 读/写自己的变量 → 有用户位、权限够 → 成功；
- 未映射的高地址、内核物理区 → 没映射 / 没用户位 → 返回 -1；
- mmap 出来的**只读**页 → 读成功、写返回 -1；
- munmap 之后再访问 → 页表项被清空 → 返回 -1。

注意返回值是 isize 的 -1，不是 u8 的 0xFF，这也是题面特意提醒的点。

**第三个请求（统计系统调用次数）必须保留。** ch4 正文只提了读和写，但本章的检查集会沿用上一章的追踪测例，所以计数的功能不能丢。计数必须放在系统调用入口、分发之前，因为“查询次数”这次调用本身也要算进去。

所以计数只能放在系统调用总入口、分发之前（入口先加一、再分发），否则“查询自身”会少算一次。实现沿用 lab1 的那套：

- `TaskControlBlock` 加一个系统调用计数数组，长度 512（最大调用号 410，每任务 1 KB，21 个任务约 21 KB）；
- `TaskManager` 提供增加与查询两个方法，用当前任务下标定位，下标越界时静默跳过，自增用饱和加法；
- 追踪的第三个分支直接返回查询结果。

### 3. 内存映射

题目列的每类错误对应一处检查，顺序也有讲究：

| 错误情形 | 检查方式 |
| --- | --- |
| 起始地址未按页对齐 | 判断页内偏移是否为 0 |
| 属性位的高位不为 0 | 与低 3 位取反后按位与，非 0 即错 |
| 属性位的低 3 位全为 0 | 低 3 位按位与结果为 0 即错 |
| 长度为 0 | 直接返回 0（什么都不做但成功） |
| 起始地址加长度回绕 | 用带检查的加法 |
| 物理内存不足 | 剩余页帧数小于所需页数 |
| 区间内已有映射 | 逐页查页表 |

几个值得说明的点：

**（1）属性位与页表项的编码错开了一位。** 用户给的属性位里，第 0/1/2 位分别表示读/写/执行；而页表项的第 0 位被有效位占了，读/写/执行在 1/2/3 位。所以**只能一位一位搬**，不能整体转换。同时无论什么属性都要补上用户位，否则用户一访问就是缺页异常。

**（2）冲突检查查的是页表，不是区域列表。** 因为 trampoline 只写页表、不进区域列表。如果只扫区域列表，用户映射到 trampoline 所在地址时会直接撞上页表建立函数里的断言，内核 panic。查页表则能正确拒绝。

**（3）判断“已映射”必须同时看返回值和有效位。** 翻译函数在中间级页表存在、叶子为空时也会返回页表项（内容全 0），只看“有没有返回值”会把 munmap 过的页误判成已映射。

**（4）冲突检查是“存在量词”。** 只要区间内**任意一页**已映射就返回 -1——因为建表是逐页进行的，任何一页撞车都会 panic。

**（5）物理页预检。** 在帧分配器里新增了一个剩余页帧数的接口，统计“未分配的空闲页 + 回收栈里的页”。够不够先看一眼，避免映射到一半才发现没内存。

**（6）不用手动切页表。** 页表是原地修改的，根页表寄存器本来就指向这个进程的根表；返回用户态时汇编会重写根页表寄存器并刷新 TLB，顺带生效。

### 4. 解除映射

整个过程分四步：

1. 系统调用入口检查对齐、长度为 0、加法回绕；
2. 进程层用“是否存在未映射页”做整段预检，**任意一页没映射就直接返回 -1**；
3. 地址空间层循环挑出“完全落在请求区间内”的区域，删除并逐页解除映射；
4. 真正回收发生在逐页解除映射里：从区域持有的帧映射表中删掉这一页（帧跟踪器被析构，物理页回到回收栈），再把叶子页表项清空。

几个细节：

- **整段预检不是可选的**：逐页解除映射里有断言，找不到页表项时还会 unwrap。少了这道预检，解除一个空区间会**panic 内核**，而不是乖乖返回 -1。
- **只匹配“完全包含”的区域**，删完一个重新扫一遍（删除会让下标前移，重扫比算下标省事）。终止性由“每轮区域少一个”保证。
- **最后那次显式析构是兜底**：此时帧映射表已经空了，但万一解除过程中途出岔子，区域一离开作用域，剩下还活着的帧跟踪器照样会被析构。这是纯 Rust 所有权的好处——**谁持有帧跟踪器，谁就让物理页活着**。

### 已知局限

- **解除映射只支持“整段”回收**：请求区间如果把某个区域切成两半，条件不满足，一页也删不掉（但函数仍返回 0）。要支持任意子区间，需要在区域上做拆分，把切出去的部分单独解除映射。
- **页表页不回收**：逐页解除只清叶子页表项，中间级页表页由页表结构自己持有，要等进程退出、地址空间被析构才还回去。反复映射/解除跨 2MB 边界的大区间会慢慢吃页。
- **物理页预检是近似的**：只算了数据页，没算建表时新建的页表页（每 2MB 一页），所以可能少算一两页。
- **末页部分覆盖的判定偏严**：区间按整页向上取整，冲突也按整页判。若请求的末页只覆盖几个字节、而该页已被别的映射占用，本实现会返回 -1。更宽松的做法是只检查“被完整覆盖的页”，并在建表时跳过已有页表项。

## 问答作业

### 1. SV39 页表项的组成与标志位

SV39 的虚拟地址 39 位，由三个 9 位的页表索引和 12 位页内偏移组成；物理地址 56 位，由 44 位物理页号和 12 位偏移组成。页表项是一个 64 位整数：

| 位段 | 名称 | 作用 |
| --- | --- | --- |
| 63:54 | 保留 | 必须为 0，留给以后扩展 |
| 53:10 | 物理页号 | 叶子项指向数据页，非叶子项指向下一级页表页 |
| 9:8 | RSW | 留给软件自用（比如标记惰性分配 / 换出 / 写时复制） |
| 7 | D | 脏位，被写过就置 1 |
| 6 | A | 访问位，被读过或写过就置 1 |
| 5 | G | 全局位，切换地址空间标识时不刷新该 TLB 项 |
| 4 | U | 用户位，用户态可访问 |
| 3 | X | 可执行 |
| 2 | W | 可写 |
| 1 | R | 可读 |
| 0 | V | 有效位 |

几条 RISC-V 特有的规则：

- 有效位置 1 时看读位和执行位：两者都为 0 表示这是**非叶子项**，指向下一级页表；否则是叶子项；
- “可写但不可读”是**非法组合**（本实验的映射 2 就是靠这一点触发读缺页）；
- 用户态访问的页必须有用户位；而 S 态要访问带用户位的页，还需要状态寄存器里的 SUM 位置 1。

### 2. 缺页

**（1）哪些异常可能是缺页导致的？**

取指缺页、读缺页、写（含原子操作）缺页三类，分别对应取指令、访存读、访存写三种访问。

**（2）发生缺页时相关寄存器的值**

- 原因寄存器：异常编号，区分取指 / 读 / 写；
- 出错地址寄存器：出错的虚拟地址，也就是“哪个地址缺页”，惰性分配全靠它反查属于哪个区域；
- 出错指令寄存器：触发缺页的指令地址，填完页表后要从这里重新执行；
- 状态寄存器：记录陷入前是用户态还是内核态、以及中断使能状态；
- 根页表寄存器：当前页表根，缺页时 MMU 用的就是它；
- 暂存寄存器：trap 入口与栈指针交换，里面是用户栈指针（上次实验已讲过）；
- 通用寄存器由 trap 入口汇编全部存进陷阱上下文，返回时再恢复。

**（3）惰性策略的好处**

- 启动快：不用真的把整个代码段、数据段从磁盘搬到内存，只记位置；
- 省内存、省页表操作：只处理真正被摸到的页，“申请 10G 只用 1M”这种场景尤其明显；
- 地址空间可以“看起来”比物理内存大；
- 天然支持共享只读页和写时复制（写时复制就是惰性分配的一个特例）。

**（4）10G 连续内存的页表开销估算**

- 10G 除以 4K 约 250 万个页，每页一个 8 字节页表项；
- 一个叶子页表页装 512 项、覆盖 2MB，所以叶子页表页约 5120 个，约 **20MB**；
- 往上一级每 1GB 一个页表页，10G 只需 10 个（40KB），再加一个根页。

总量级约 **2×10⁷ 字节**，相当于每 2MB 数据多付一页页表，约 0.2%，不算离谱——但这是“真的用满 10G”的代价，而惰性分配能让“申请了 10G 只用 1M”的程序只付 1M 的页表钱。

**（5）实现惰性策略的思路**

- 映射调用只登记一条虚拟内存区域记录（起止、权限、是否已分配），**不分配物理帧、不写页表项**；
- 缺页时在陷阱处理里抓到三类缺页异常，用出错地址找到所属区域：找不到、或访问类型超出该区域权限就杀进程；找到就分配一页、清零（或从文件、换出区读入）、按区域权限加用户位填页表项；
- 从陷阱返回时回到出错指令地址重新执行那条指令，这次就能过；
- 优化：区域记录用有序结构或位图加速查找，或者直接用页表项的 RSW 位标记“这一页是惰性的”，省掉一次查找。

**（6）换出时页面失效在页表项上的表现**

清掉有效位（通常连同读/写/执行一起清），这样任何访问都会触发缺页；物理页号字段可以复用成“换出槽号”，RSW 两位标记这一项的状态（未分配 / 惰性 / 已换出）。缺页时用出错地址定位虚拟页，把页换回来、重填页表项、重新执行即可。

### 3. 双页表与单页表

**（1）单页表情况下如何更换页表？**

只在**进程切换**时换：把新进程页表的根页号写进根页表寄存器，再刷新 TLB。因为内核和用户共用一张表，同一进程在用户态和内核态之间来回跑时不用换表。

**（2）单页表下如何让用户态访问不到内核页面？**

靠用户位：内核页的页表项不设用户位，并且状态寄存器里的 SUM 位保持 0（这样内核态也不许访问带用户位的页）。用户态一碰就是缺页。注意不能用“页表项无效”来做隔离，因为内核自己要访问这些页，无效项会把自己也拦下来。

**（3）单页表的优势**

- trap 进出不用切根页表寄存器、不用刷新 TLB，系统调用和中断开销明显更低；
- 内核可以直接解引用用户指针，跨地址空间拷贝之类的逻辑简单；
- 不需要 trampoline 那段“同一份代码映射在两个地址”的技巧，也不占额外一张页表。

**（4）换页表的时机**

- **双页表（本项目 ch4）**：每次 trap 都要换两次——进入内核时汇编切到内核页表并刷新 TLB，返回用户态时再切回用户页表并刷新；如果中途发生了任务切换，返回时用的是**新进程**的页表。
- **我写单页表 OS 的话**：只在任务切换时换一次。上下文切换回来之后、返回用户态之前写一次根页表寄存器并刷新就行；同一进程的 trap 进出完全不碰它。如果想兼顾侧信道防护（KPTI），那就要在用完内核页表之后尽快切回用户页表，退化成“每进一次内核换两次”。

## 对本次实验的看法（选填）

- 映射与解除映射的简化（只做匿名映射、不做失败回收）很合理，能在一章之内讲清“虚拟页、物理页、页表项”三者的关系。
- 题面对两个边界说得不够明确：一是长度向上取整后**末页多出来的部分**算不算冲突，二是解除映射**只覆盖某个区域一部分**时该拆还是该拒绝。这两处不写清，实现起来只能靠猜。
- 工作量适中，主要时间花在调试“为什么漏了用户位”“为什么解除映射直接把内核断言炸了”，这两个坑都很值得踩一次。
